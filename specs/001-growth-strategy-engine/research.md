# Research: Growth Strategy Engine

**Feature:** 001-growth-strategy-engine
**Date:** 2026-04-04
**Status:** Complete

---

## Decision 1: Growth Path Content Storage

**Decision:** Store path content as a single JSONB column on `growth_paths` table, following the V1 pattern of collapsing strategy sub-tables to JSONB.

**Rationale:** Constitution I (simplicity) — the V1 engineering amendments already validated this pattern by collapsing 6 strategy sub-tables to 3 JSONB columns. Growth path content varies by path type (Portfolio has scaling plan, Income has funding map, etc.), making a single flexible JSONB column more appropriate than type-specific columns. Content is always read/written as a unit (never queried field-by-field).

**Alternatives considered:**
- Separate tables per path content type (12+ tables) — violates constitution I, massive schema complexity for no query benefit
- Separate columns per content section — rigid, requires schema changes for content evolution
- Document store (MongoDB) — adds a new database dependency, violates constitution II

---

## Decision 2: Action Items — Embedded JSONB vs Separate Table

**Decision:** Embed action items as JSONB within `growth_paths.action_items` column, following the V1 strategy JSONB pattern.

**Rationale:** Action items within a growth path are always read/written as a set. Cross-path action priority ranking is computed at read time from all paths' action items (no need for cross-table joins). The V1 pattern (`strategies.action_plan` JSONB with `{items: [...]}`) is proven. Item IDs within JSONB are CUID2 for stable references.

**Alternatives considered:**
- Separate `growth_path_action_items` table — enables SQL queries on individual items but violates constitution I since we never query individual items outside their path context. Cross-path ranking is an in-memory sort, not a SQL join.
- Shared action items table across V1 strategies and V2 growth paths — over-abstraction, different semantics

---

## Decision 3: Cross-Path Links Storage

**Decision:** Store cross-path links as JSONB on `growth_strategies.cross_path_links` column. Regenerated when any path is generated or regenerated.

**Rationale:** Cross-path links are generated by AI as part of each path generation call. They are always displayed as a set on the dashboard. There is no need to query individual links. Storing on the strategy (parent) rather than on individual paths avoids duplication and keeps the "cross-path" semantics clear.

**Alternatives considered:**
- Separate `cross_path_links` table — SQL queryable but never needed; links are always loaded with the strategy dashboard
- Store on individual paths — each path would only have links involving itself, making dashboard assembly harder

---

## Decision 4: Unlock Event Tracking

**Decision:** Track unlock metadata directly on `growth_paths` table (unlock_type, unlocked_at, unlock_trigger_details columns) rather than a separate unlock_events table.

**Rationale:** Each path unlocks exactly once (it never re-locks). One unlock event per path = one-to-one relationship. Constitution I says prefer one table over two when the relationship is 1:1. The spec's analytics requirements (organic vs manual unlock ratio, unlock rates) are satisfied by querying these fields directly.

**Alternatives considered:**
- Separate `unlock_events` table — normalized but 1:1 with growth_paths, adds unnecessary join
- JSONB field on growth_paths — less queryable than typed columns for analytics aggregations

---

## Decision 5: Feature Flag Implementation

**Decision:** Add a `feature_flags` JSONB column to the existing `tenants` table. Growth Strategy is gated by `tenants.feature_flags.growth_strategy_enabled`.

**Rationale:** Constitution I — no new table for a single boolean flag. The tenants table already has a `configuration` JSONB column, but feature flags are semantically distinct from configuration. A dedicated `feature_flags` JSONB column keeps concerns separated while avoiding a new table. Checked at the middleware/service layer.

**Alternatives considered:**
- Merge into existing `tenants.configuration` JSONB — muddies the distinction between config and feature flags
- Separate `feature_flags` table — over-engineered for a single flag at MVP
- Environment variable — not per-tenant, can't do gradual rollout

## Decision 6: Portfolio Growth Wrapping Existing Strategy

**Decision:** Portfolio Growth path references the existing `strategies` table records. The path's `content` JSONB contains the new scaling plan elements. The existing strategy data (action plan, roadmap, micro-plan) remains in the `strategies` table unchanged. Portfolio Growth path links to the active strategy via `strategy_id` FK.

**Rationale:** No data duplication. Existing V1 strategy endpoints continue to work by reading from the same `strategies` table. The Growth Strategy dashboard assembles Portfolio Growth by combining the path's scaling plan content with the referenced strategy's existing data. This achieves FR-03 (wrapping without data loss) and FR-18 (backward compatibility) simultaneously.

**Alternatives considered:**
- Copy strategy data into Portfolio Growth JSONB — data duplication, sync headaches, violates single source of truth
- Replace strategies table with growth paths — breaks V1 API backward compatibility

## Decision 7: Path Generation AI Architecture

**Decision:** One prompt template type (`growth_path_generation`) with path-type-specific instructions injected as context. Separate prompt template for cross-path analysis (`cross_path_analysis`). Uses the existing AI client with circuit breaker and retry logic from V1.

**Rationale:** All four path types follow the same generation flow (identity context + prior paths + path-specific instructions → structured output). The path type is a parameter, not a fundamentally different prompt structure. The existing AI client (Anthropic SDK wrapper, retry logic, circuit breaker) from V1 is reused unchanged.

**Alternatives considered:**
- Separate prompt template types per path — 4 template types for the same flow structure; harder to maintain
- New AI client — V1's client already handles all needed patterns (timeout, retry, circuit breaker)

## Decision 8: Export Architecture

**Decision:** On-demand generation (no caching). Zip assembly in-memory using `archiver` npm package. AI summary uses a lightweight prompt (~200 input + ~150 output tokens). Export served as streaming response.

**Rationale:** Exports must always reflect current state (spec FR-12: "generated on-demand, not cached"). In-memory zip avoids temp file cleanup. The `archiver` package is well-maintained (60M+ weekly downloads), battle-tested for zip creation, and is the only new dependency needed for this feature.

**Alternatives considered:**
- Pre-generate and cache exports — stale data risk, cache invalidation complexity
- Temp files for zip — requires cleanup logic, disk management
- `jszip` — similar capability but `archiver` has better streaming support for Express responses

---

## Decision 9: Export Freshness Detection

**Decision:** `export_history` table records each export with a snapshot of identity version and path versions at export time. Staleness is detected by comparing current versions against the last export's snapshot.

**Rationale:** Simple comparison: if `identity_versions.version > last_export.identity_version` OR any `growth_paths.version > last_export.path_versions[type]`, the export is stale. This is a read-time check on the dashboard, not a background job.

**Alternatives considered:**
- Event-driven staleness flag — requires updating a flag on every identity/path change, more write paths
- Timestamp-based comparison — less precise than version comparison

## Decision 10: Blueprint PDF Extension

**Decision:** Extend the existing Puppeteer-based Blueprint service with new HTML template sections for growth paths. Conditional rendering based on which paths are unlocked.

**Rationale:** V1 already has a working Blueprint PDF pipeline (HTML template → Puppeteer → PDF). Adding sections to the HTML template is incremental. No new dependencies or rendering approaches needed.

**Alternatives considered:**
- Separate PDF for growth strategy — users expect a single unified document
- New PDF library — unnecessary when Puppeteer already works

## Decision 11: V3 Backward Compatibility

**Decision:** When the feature flag is on, existing V1 strategy endpoints (`GET /api/v1/strategies`, etc.) continue to read from the same `strategies` table. No proxy or redirect needed — the data is in the same place. New growth strategy endpoints are additive.

**Rationale:** Because Portfolio Growth references existing strategies (Decision 6), the V1 endpoints naturally continue to work. No adapter layer needed. Growth Strategy endpoints are new paths (`/api/v1/growth-strategy/*`), not replacements.

**Alternatives considered:**
- Proxy V1 endpoints to Growth Strategy endpoints — unnecessary complexity since data stays in place
- Deprecate V1 endpoints immediately — breaks existing integrations

## Decision 12: Progressive Unlock Evaluation

**Decision:** Evaluate unlock conditions synchronously on relevant triggers (task completion, action item completion, login). No background job or polling.

**Rationale:** Unlock conditions are simple count/date checks:
- Path 2: `COUNT(completed micro-plan tasks from Portfolio Growth) >= 2`
- Path 3: `Path 1 generated AND Path 2 generated AND COUNT(completed action items from Path 1 or 2) >= 1`
- Path 4: `3 paths generated AND user.created_at <= 14 days ago AND has_activity_in_period`

These are cheap queries triggered at specific events (task completion writes to activity_logs → check unlocks). No need for scheduled evaluation.

**Alternatives considered:**
- Cron job to evaluate unlocks — unnecessary overhead, delayed feedback
- Pub/sub event system — over-engineered for synchronous checks

---

## Decision 13: Rate Limiting for Path Generation

**Decision:** 1 generation per path per hour, enforced via query against `growth_paths` table (`updated_at` or `generated_at` column). Different paths can generate in parallel.

**Rationale:** Per the spec (FR-06): "1 call per path per hour." Query-based enforcement follows the V1 simulation rate limiting pattern (query-based, no sessions table). The rate limit is per path type, not global, so users can generate Income path immediately after Portfolio path.

**Alternatives considered:**
- Redis-based rate limiting — new dependency for a simple per-user-per-path check
- In-memory rate limiting — doesn't survive server restarts

---

## Decision 14: Non-Blocking Path Generation UX

**Decision:** Synchronous AI call with 30-second timeout (matching V1 strategy generation). Path status set to "generating" before the call, updated to "generated" or reverted to "unlocked" on completion/failure. Frontend polls or uses SSE for status updates.

**Rationale:** The spec says path generation is "non-blocking" (FR-09) — the user can navigate away. However, V1 uses synchronous calls with timeouts. For consistency, keep synchronous backend calls but return immediately to the client with "generating" status. The client polls the path status endpoint.

**Alternatives considered:**
- WebSocket for real-time updates — new infrastructure for a single use case
- Background job queue (Bull/BullMQ) — new dependency, V1 doesn't use queues
- Server-Sent Events — simpler than WebSocket but still new infrastructure; consider for post-MVP

## Decision 15: New Dependency: archiver

**Decision:** Add `archiver` (npm) for zip file generation in the markdown export feature.

**Rationale:** Constitution II requires justifying every dependency. `archiver` is needed because:
- Node.js has no built-in zip creation API
- The export feature requires creating a multi-file zip archive
- `archiver` is the most mature zip library (60M+ weekly downloads, actively maintained)
- Cannot be solved with 20 lines of code (constitution II)

**Alternatives considered:**
- `jszip` — comparable but `archiver` has better streaming support
- `yazl` — lower-level, more code to write
- Shell out to `zip` command — platform-dependent, harder to test
